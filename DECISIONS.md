## 2026-10-08 → 2026-10-10 — the substrate

25. *(2026-10-08; revised 2026-10-09)* A feature is not defined; its contract is. Every feature has a name, zero or more parents, an owner, a maturity claim with evidence, `affects` edges, and a derived mapping to the mechanism. Size and meaning are the author's — a capability, a flow, a button; there is no `kind` field and no typed hierarchy. Depth is unlimited. **Many parents, one owner** (revised from "one parent, many affects"): a feature may sit under several features — the cross-cut as people draw it — and ownership inherits only along a single line; a feature with several parents names its own owner (defaulting to the single user in single-player). A change to a shared feature needs its owner's signature and notifies the owners of every feature that uses it (manufacturing's "where-used"). So "whose signature" still has one answer. **Mappings are derived; nodes never are**: the derived layer never creates features from code structure. "A promise the product makes, that someone is accountable for" is help text for sizing, not a rule.
26. *(2026-10-09)* The vocabulary is four nouns. **Product**: the root (not "application" — a software word — and not "project", which ends). **Feature**: any node beneath it. **Change**: a unit of work against one or more features; its signers are the union of their owners; a Linear ticket, a GitHub issue, a milestone or a brainstorm are all changes. **Decision**: what a person wrote. **Session** is derived and belongs to the adapters, not the contract.
27. *(2026-10-09, provisional)* **Identity.** Every change (and feature) gets a generated UUID by default (time-ordered); external entities map onto it. The map is what makes the framework agnostic: a Linear ticket, a Jira issue, a Google Doc, even a Slack message can each bind to a change, and a change can carry several external references. Refs live on the record; the map is a derived index. Humans never type a UUID: folders and prompts use the external key or a slug, `id:` is in the frontmatter, references inside files point only at ids, and the CLI accepts a unique prefix.
28. *(2026-10-10)* **Storage: records are the truth, a graph is the index, the schema is independent of both.** Phase 1: a flat store of records as files — changes, features, decisions and **sources** (an external thing: ticket, doc, PR, message; a small record created on first mention) — human-readable and in git. Edges are typed (`binds` — identity, one change per source, validated; `links`; `evidence`; `parent`; `affects`; `touches`; `decided`; the set is data) and **declared on the record that made them** in frontmatter, never in prose; reverse edges are never written. **Authored edges** (declared on intent) live on records; **observed edges** (noticed in a session) are appended to that session's record, which has one writer and is append-only, so they carry provenance and merge without arbitration. An embedded graph database (or SQLite) is the **index**: rebuilt from the files, disposable, the only thing queries hit. The CLI is the schema: the library is the only writer adapters use and validates on write; hand edits are validated at the next index build and invalid records are reported as drift. No priority chain: declared and observed disagreeing is drift, surfaced, never silently resolved. **The schema is defined once, independent of storage** — entities, fields, edge types, validation — so Phase 2 implements the same schema over a hosted server database, where the roles flip: the organisation's graph database becomes the truth, agents query it through the MCP and people through the web, and the files become the export, the open format and the local mode. The hosted graph is the product. *Provisional:* a request is not an entity but a source with a `requested` edge from the change triage created; a source with no change bound is the queue.
29. *(2026-10-10)* **The context graph is the substrate; the alignment thesis is a layer on it.** The work tool, the framework and the business are one object at three distances — the local graph, the shared graph, the alignment layer over the shared graph. Project management is not a layer over the developer tool; it is the same record with more readers, more writers and one more field family (who owns, who signs). The substrate may carry its own name, separate from the alignment product. *(The resynthesis of `THESIS.md` on this date reorganised the document around this.)*
30. *(2026-10-10)* **Humans and agents are the same kind of participant.** A principal is a person or an agent; every record carries its writer; owners and authorities may be either. Where a human is required is a policy on the tree (by maturity level and scope), not a property of the system — day one, every scope requires a human; as autonomy grows, organisations move that line, and the model does not change. Agent-to-agent coordination happens through the record (the blackboard), never through messages, so every action in a factory of agents is a record with provenance. The tenet "humans author decisions" is restated: *a decision is authored by a principal with authority for its scope, and humans set which scopes require a human.* Phase 1 consequence: one field — every record carries its writer, and `owner` accepts an agent.
