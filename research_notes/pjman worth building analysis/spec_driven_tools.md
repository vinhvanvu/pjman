# Spec-driven development tools and in-repo agent-workflow frameworks vs. pjman Phase 1

*Researched 2026-10-09. All GitHub numbers were pulled live from the GitHub REST API on 2026-10-09 (≈21:10 UTC) unless another date is given. npm download counts are the npm registry's "last month" window 2026-09-08 → 2026-10-07; PyPI counts are pypistats "last_month" as of 2026-10-09. The pjman Phase 1 shape being compared against (from `THESIS.md`): one folder per **change** bound to an external ticket/issue/doc, holding plan + decisions-with-rationale + feedback + evidence (PRs), strict frontmatter contract, typed edges to features and sources, authored vs. derived state kept apart, a derived index, a CLI/library emitting JSON, harness-agnostic.*

The six capability questions used throughout: **(a)** decisions with rationale as a first-class record; **(b)** binding a unit of work to an external ticket/issue/doc; **(c)** relationships between units of work or to product features; **(d)** authored vs. derived state separated; **(e)** machine-readable contract other tools read; **(f)** CLI/library/index rather than only markdown templates and prompts.

---

## Key question 1 — Tool-by-tool profile (artefacts, location, agents, procedural/declarative, licence, stars, maintainer, launch, activity)

### Takeaway
Every significant tool in this category is a **procedural pipeline** (constitution/steering → spec → plan → tasks → implement, in some order) that writes **markdown into a dot-folder in the repo** and is driven by **slash-command prompts**; the "unit" is a *feature/spec/change/mission/track*, not a ticket-bound change with decisions and evidence. Only OpenSpec, Spec Kitty, Taskmaster, Beads and GSD have any CLI/JSON surface at all, and none has a typed edge model, an authored/derived split, or a decision record with rationale as a schema object. The one tool that does model decisions as typed objects (Memex) stores them in Postgres outside the repo and had 29 stars.

## Key question 3 — What users say works and fails (ceremony, drift, abandonment, single-change scope, lock-in)

### Takeaway
Practitioner evidence is consistent across two years of HN threads: the pipelines are praised as *process discipline* and token hygiene, and criticised for **spec bloat on small changes**, **spec↔code drift that makes maintenance "not worth it"**, and **reverting to small hand-written markdown or ADRs** — the maintainers themselves concede the slop problem.

### Cited Findings
- Thoughtworks Technology Radar, Nov 2025, ring **Assess**: "the workflows remain elaborate and opinionated… some generate lengthy spec files that are hard to review, and when they produce PRDs or user stories, it's sometimes unclear who their intended user is", possibly showing "that handcrafting detailed rules for AI ultimately doesn't scale"; the page notes the blip is from a previous volume (not carried into the current 2026 edition) — [Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/spec-driven-development)
- "Spec-Driven Development: The Waterfall Strikes Back" (fzaninotto), 225 pts / 191 comments, 2025-11-15: author "never seen instances of a coding agent doing exactly what I had in mind in the first try… so there must be iterations"; constantcrying: "the tiniest feature you want to add requires extremely complex manipulation of the spec"; cushychicken warns calcified specs trap developers; thomascountz found Spec Kit "heavy-handed and unwieldy"; what works per canterburry: "20x ROI on well defined, comprehensive, end to end acceptance tests that the AI can run"; ErrantX treats Spec Kit specs "as context entry points rather than fixed blueprints" — [HN](https://news.ycombinator.com/item?id=45935763)
- "Understanding SDD: Kiro, Spec-Kit, and Tessl", 128 pts / 32 comments, 2025-10-16: iamsaitam — Kiro turned a small bug fix into 4 user stories with 16 acceptance criteria; ctxc: "generated steps that were the equivalent of Tony Stark building a robot from scratch in a cave when 'just screw this bolt on' would have sufficed… at some point it wasn't worth correcting it anymore" (abandonment); yoaviram after a 10-day Spec Kit build: "Most tests were failing, and the build was not successful… my confidence in the code is low"; iamdeedubs: "when does it merge all this specs into a single ground truth… a huge missing step"; esafak: values simple markdown for tracking progress, "I don't see value in the formalism beyond that" — [HN](https://news.ycombinator.com/item?id=45610996)
- "What's the Deal with GitHub Spec Kit", 2025-10-14: yodon enjoys it but says tutorials are "pretty elementary" and lack guidance for "incremental improvements or refactorings to a huge legacy code base" or spec changes mid-implementation ("BDUF is still hard") — [HN](https://news.ycombinator.com/item?id=45577377)
- OpenSpec thread, 204 pts / 100 comments, 2026-09-16: what works — "process flow" more valuable than specs; token efficiency; org-wide standard artefacts avoid "snowflake agent sessions". What fails — one developer found "huge divergence from spec to code" on two large projects and challenged readers to verify with a frontier model; "prose can never enumerate all the behaviors required of code… the spec almost immediately becomes out of date"; orgs report "large set of multiple markdown documents, each that need review" full of "slop"; "some engineers abandoned OpenSpec entirely, reverting to single markdown files or architecture decision records"; experienced devs prefer a "small, human written spec" plus ADRs and invariant logs; GSD reported "~4x" more token-hungry than OpenSpec. Maintainer TabishB: "if no thought or effort is put into the spec, it can turn into unreadable slop", committing to make specs "a lot more succinct and iterative". Reported fit: single complex features, greenfield days-to-weeks, solo/small teams; poor fit: large multi-dev codebases with evolving requirements, 6+-month projects without active spec maintenance, teams >25–30 without a mandate — [HN](https://news.ycombinator.com/item?id=49734264)
- "Specsmaxxing" thread (OpenSpec user alasano): "I've stopped doing it entirely and just archive directly after implementation… When you do the sync process, it just keeps drifting and drifting until you have duplication and contradictions across specs… maintaining the main specs is not worth it"; jochem9: "when a spec changes, AI needs to find the relevant code to change it. It's pretty easy to miss something in large codebase"; energy123 on structured YAML specs: "coming up with a good schema that doesn't handicap you or add cognitive burden, compared to the freeform flexibility of md/txt, is a challenge" — [HN](https://news.ycombinator.com/item?id=47994433)
- Beads abandonment thread, 84 pts / 51 comments, 2026-01-04 (wild_egg, who built a replacement): "every release made it slower and more frustrating to use", fighting "its background daemon took to syncing the wrong things at the wrong times"; kept only "graph-based task dependencies" in "a single file bash script built on coreutils managing flat files"; shankspeaks: "Beads has great primitives, but become a bit unwieldy in trying to become something 'everyone' can use"; commenters value "fewer moving parts" and flat files avoiding "vendor lockin + slow network calls" — [HN](https://news.ycombinator.com/item?id=46487580)
- spec-compare's synthesis: "Most SDD tools excel when requirements are clear upfront but struggle with iterative changes like 'change button from blue to green'"; Kiro/BMad "sledgehammer to crack a nut"; Spec-First tools (Spec Kit, Kiro, BMad) have an "unclear maintenance story… may abandon specs after initial development"; "We might end up with the downsides of both MDD and LLMs: Inflexibility and non-determinism" — [critical-analysis.md](https://github.com/cameronsjo/spec-compare/blob/main/docs/critical-analysis.md); [README](https://github.com/cameronsjo/spec-compare)
- Tessl critiques (reviewer's opinion): non-deterministic "compiler" — regenerating from the same spec yields different code; "sledgehammer problem": minor changes require amending major spec documents; JS-only in practice — [codemyspec](https://codemyspec.com/blog/tessl-review)
- GSD reception: "divided, with some saying it would be useful for non-engineers but represents over-engineering for experienced developers" — [horadecodar](https://horadecodar.com.br/get-shit-done-comparativo/)
- Lock-in signal in reverse: OpenSpec supports ~35 harnesses and Spec Kit 30+, so the open tools compete on *being* harness-agnostic; the proprietary ones (Kiro, Tessl, Augment, Traycer) are single-harness by construction — [OpenSpec supported-tools](https://github.com/Fission-AI/OpenSpec/blob/main/docs/supported-tools.md); [spec-compare comparison](https://github.com/cameronsjo/spec-compare/blob/main/docs/comparison.md)

### Inferences
- The recurring "what works" (short hand-written spec, ADRs, acceptance tests, the *process* rather than the documents) maps closely to pjman's tenets ("Humans author decisions; agents do everything else"; "Prescribe what gets recorded, never how the work is done"), and the recurring "what fails" (AI-generated spec volume that then rots) is what pjman's "never a wiki" / drift-surfaced stance is designed to avoid — but the OpenSpec thread's warning about multi-markdown artefact explosion applies to any per-change folder design if agents are allowed to fill it.
- "Single-change scope" is a confirmed weakness of the category: spec→plan→tasks per feature with no cross-feature model; the demand for "when does it merge into a single ground truth" and for cross-repo planning (OpenSpec Stores) is evidence that a feature tree / product-level record is wanted and missing.

### Gaps
- No quantitative retention/abandonment data exists for any tool; evidence is anecdotal HN threads plus one maintainer concession. No Pragmatic Engineer or InfoQ survey on SDD adoption was found.
- No HN or long-form critique threads of BMAD or GSD with substantive comment counts exist (best BMAD story 4 points, best GSD 12 points), so their user sentiment is drawn from secondary blogs only.

### Inferences
- Stars track launch virality (GSD's 50K in three months, then an org move and a reset to 10K; Taskmaster flat after development stopped) more than sustained use; monthly downloads are the better signal, and on that signal OpenSpec is ~30× any other open tool.
- Spec Kit's continued ~6–7K stars/month through 2026 with weekly releases shows GitHub is still investing; it is the incumbent any new in-repo framework will be compared with by default.
- There is no evidence of enterprise adoption statements for any *open* framework (no customer logos, no case studies found); enterprise claims exist only for Kiro (AWS) and the funded platforms.

### Gaps
- Cumulative download totals for Spec Kit (`uv tool install` is not fully captured by PyPI stats) and for GSD Core's new package name were not obtained.
