# 06 — Generality and the actor model

*Adversarial review of SCHEMA.md draft v2 against two claims: (1) the entities are domain-agnostic ("nothing in the entities says code"); (2) the actor/session model gives every write provenance and lets agents coordinate through the record. Read: SCHEMA.md, THESIS.md, DECISIONS.md 22/25/26/28/30, LAYERS.md, the `.pjman/` store (22 records), the DARKFOG `.claude/` persistence layer (README, templates, M3.20/M3.20a, `lighting/rejected.md`, `pre-work/INDEX.md`), the session board's DESIGN.md, and the pjman git log.*

## Verdict

Claim (1) holds for field names and fails for semantics. The record types carry no software words, but three things underneath them do: provenance (a layer-0 *requirement*) is satisfied in Phase 1 only by git commit trailers, so a store that is not a git repository has no provenance at all; the `observed` half of the two-truths model is derived-only and adapter-written, so the thesis's "drift detection degrades to human report" is impossible by the schema's own A/D rule (a human reporting observed state is a hand edit to a derived field, i.e. drift); and the status vocabulary is Linear's default workflow states renamed, with no state for the thesis's own "authorize the intent" moment. Claim (2) fails in Phase 1, not Phase 3: with `on_behalf_of` pruned and `writer` on a session fixed to the harness actor, the second-user milestone (two people running `agent:claude-code` on one store) produces records whose human cannot be recovered. "Spawn is a session, never an actor" is unenforceable because actors are created on first mention and nothing distinguishes a definition from a handle an adapter typed. "Agents coordinate through the record" is true only for append-only observed edges; there is no claim, no ask, no handoff, and no conflict rule for authored fields. The store's own 26 commits carry zero `Pjman-Session` trailers, so the walk-through does not meet layer 0 either.

## Hospital walk-through

Case: a clinical informatics team at a hospital changes the sepsis order-entry protocol in Epic. The driver is a P&T committee recommendation; the artefacts are a ServiceNow ticket, a PolicyStat policy revision, an order-set build, a validation sign-off, a go-live date, and a retirement of the old order set.

| Concept | Maps to | Strain |
|---|---|---|
| The hospital's CPOE configuration | `product.md` "Sepsis order entry" (one per store) | "Product" is a product-development word; the informatics team has a *system* and *policies*, not a product. Tolerable. |
| Sepsis protocol, its order sets, the alert | `features/` tree, `touches` from the change | Works. No `kind` is a plus here. The derived "mapping to the mechanism" has no deriver in this domain, so `touches` is the whole mapping. |
| The protocol change | `changes/sepsis-v4/change.md` | Works as a container. See status below. |
| ServiceNow ticket INC-4411 | `sources/servicenow/inc-4411.md`, `binds` | Works; `source_kinds` is config. |
| PolicyStat policy #882, revised by this change | `sources/policystat/882.md` | **Fails on `binds`.** The policy is the change's external identity in the governance system, but it is a long-lived document revised by every protocol change for ten years. "A source binds at most once" is ticket-shaped (one-shot). Either the `key` must encode a revision (`882@v4`, invented) or the policy is `links` not `binds` and the change has no governance identity. |
| P&T committee minutes, Joint Commission standard NPSG.03.06.01 | `sources/minutes/...`, `sources/regulation/...` via `links` | Works. |
| Committee approval to proceed (before build) | **No status.** `planning` → ??? → `active` | The thesis (lifecycle step 4) says "authorizing the intent and accepting the result are separate moments." The vocabulary has `review` ("work complete, awaiting acceptance") and nothing for "approved, not yet built." This is the single most important state in clinical governance and it has no home. Hospital `approved` must be mapped to `planning` or `active`, both wrong. |
| Build complete, validation pending | `review` | Works. |
| Validated but not yet live (go-live in two weeks) | `done` ("Accepted") | `done` conflates accepted with in-effect. A protocol that is accepted but not live is the normal state for weeks. |
| Old order set retired | `dropped`? `done`? | "Closed without acceptance" is wrong; retirement is the planned end of an accepted thing. No `retired`/`sunset`. (Intake bucket 14 lists "retire" as a first-class request type; the vocabulary cannot express its completion.) |
| The P&T committee decided | `decided_by: ???` | **Fails.** `kind` is `person` or `agent`. The decider is a committee. The only workaround is `person:p-and-t-committee`, which lies about `kind` and defeats "same kind of participant." The same hole exists in software (an architecture review board). |
| A committee meeting; a two-hour Epic build session | `sessions/` | **Fails.** A session is "derived, one writer (the adapter that produced it), append-only, never hand-edited," with a required `agent` field. Nothing in a hospital produces sessions. So no observed edges exist, and the only way to say "at Tuesday's meeting we noticed the alert affects the ICU set" is a hand-written session, which the schema permits once (`ext.bootstrap`). The field name `agent` on a human-run session also contradicts decision 30. |
| What Epic currently shows (the order set as built) | `source.observed` | **Fails.** `observed` is D, "written only by a sync adapter." There is no Epic sync. The informaticist who opens Epic and reports "the order set still has the old dose" cannot write that anywhere structured; if she edits `observed` the validator reports her edit as drift. The thesis's "degrades to human report" has no schema path. |
| Drift (policy says v4, Epic has v3) | Index compares `observed.status` to `status` | Unreachable, per the row above. Drift is defined only over `observed.status`, i.e. a tracker's state field; drift of *content* (dose, criteria) is not a thing the schema can represent in any domain. |
| Where the store lives | `~/.pjman/stores/sepsis/` (no repository) | Works for location. **Breaks provenance**: "In Phase 1 git provides the rest for free: `git blame` gives field-level history, and an adapter that commits records writes a `Pjman-Session:` trailer." No git, no history, no trailer, no audit log (hosted only). The layer-0 requirement "every write has provenance" is met by nothing. "Derived fields match what their deriver last wrote" also needs a baseline, which only git supplies. |
| Who authored what, when | `writer`, `created`, `updated` | Self-asserted strings in a text file. Fine in a repo with blame; in the hospital store, anyone can type `writer: person:cmo`. |

Is git baked into layer 0? Yes, twice: provenance (above) and the derived-field drift rule (the "last written" baseline). Decision 28 says "human-readable and in git" and the thesis says "records are files, one per node ... in git." The location section allows a non-repo store, but nothing else in layer 0 works there. Either the location rule or the provenance rule has to give.

## DARKFOG walk-through

DARKFOG's `.claude/` layer has: brainstorm topics (topic-root `decisions.md`, `conversations.md`, `rejected.md`); brainstorm sessions under a topic (`summary.md`, `exploration.md`, `graduated.md`, `rounds/`); milestones (`summary.md` with `M_id`, `depends_on`, `origin_brainstorm`, `started`, `completed`, `abandoned_reason`; `plan.md`, `decisions.md`, `conversations.md`, `commits.md`, `rounds/`); pre-work items (promotable to milestones); rounds (`prompt.md`, verbatim `agent-N-role.md`, `verdict.md` with A/B/C/D).

What maps cleanly:
- Milestone, pre-work item, brainstorm session → `change`. `plan.md`, "why not a milestone", status notes → body.
- Milestone decisions, topic-root decisions → `decision` (under the change, or at store root with `touches`).
- `MILESTONES.md` section, commits, `world/setting/*.md` → sources (`file`, `git-commit`); `commits.md`'s "which decision this advances" → `decision.links` to the commit source.
- Subagent worktrees `agent-a6d1...` → sessions with `parent`.
- `verdict: A/B/C/D`, `role: adversarial` → `ext`.

What has no home:

1. **Containment and change-to-change edges.** `M3.20` was split into `M3.20a` and `M3.20b`; `M3.19` has stages S0, S1, S1a–S1f, Layer 1a, 1b.4; `depends_on: [M3.19]`; pre-work "promoted to M3.x" (`abandoned_reason`). v2 has no edge from a change to a change: `parent` was pruned, `links` accepts source ids only, `supersedes` exists only on decisions. "A milestone is a change" holds for a flat set and fails the moment milestones contain changes, which in this project is every milestone. The same failure will hit the Linear binding in Phase 2: parent issues, sub-issues, projects and cycles are all change containment, and the sync has nowhere to put them.
2. **Rounds as evidence.** A round is a parent session with N child sessions plus a verdict. The verdict can be a `proposed` decision authored by the judiciary agent and `decided` by vinh. But the decision cannot cite the four agent runs: `decision.links` is `[source id]`, and a session is not a source. **No record in v2 can reference a session except via the envelope's own `session` and a session's `parent`.** Evidence for a decision that lives in sessions is unrepresentable until layer 4's `evidence` edge, and even that is described as decision/feature → evidence, with sessions not named as a target.
3. **The prompt.** DARKFOG saves `prompt.md` verbatim because the prompt *is* the identity of an ad hoc agent. v2 drops it: a subagent is a session whose `agent` is the harness (see Actor failures, scenario 3).
4. **Rejected directions.** `rejected.md` entries (what was proposed, why it died, which round killed it, what replaced it) are the project's most reused records ("prevents re-relitigating"). Decision statuses are `proposed · decided · superseded · reverted`. A rejected direction was never decided, so `reverted` is wrong; `superseded` requires a newer decision pointing at it, which does not exist for "no replacement; question closed." The nearest encoding is an inverted decision ("do not do X", `decided`), which loses the proposal/rejection distinction and the `killed_by` edge (decision → round → sessions, again unrepresentable).
5. **Brainstorm topic.** `lighting`, `fog-look`, `world-scale`, `vision` aggregate sessions across months with topic-level decisions. A topic is sometimes a feature (`lighting`), sometimes not (`vision`, `world-scale`). Without `parent` on change, a topic is either a feature it isn't, or a long-running change with no children.
6. **Graduation.** `exploring → graduated → abandoned`. `graduated` maps to `done` ("Accepted"), which is false: a brainstorm that graduates was not accepted, it spawned milestones. The `graduated_to` edge is change → change (item 1).
7. **Transition dates.** `drafted`, `started`, `completed` per milestone. v2 has `created` and `updated` only; "when did this go active" is recoverable from git blame on `status` and from nothing else. (The hospital case needs approval and go-live dates for the same reason.)
8. **`abandoned_reason` required when abandoned.** Body in v2; DARKFOG and the pre-work INDEX make it a validated field. Minor, but it shows the vocabulary needs per-status required fields, which the schema only has for decisions.
9. **`conversations.md`.** Session highlights written by Claude *during* the session about its own run. This is exactly a session record, which v2 says is adapter-written and never hand-edited. Until the Claude Code adapter exists, every DARKFOG session would be a bootstrap-exception.

## Vocabulary neutrality

The default vocabulary is `open · planning · active · blocked · review · done · dropped`. Its lineage is visible: the session board's lane table (`DESIGN.md` lines 95–106) maps `started/planning/implementing/reviewing/in-review/blocked/done` onto Linear's `Todo / In Progress / In Review / Blocked / Done`, and the store's own `pjman.yaml` ships `implementing: active, merged: done, closed: dropped` as the sample mapping. `merged` is a git word in the reference configuration.

Evidence it is software delivery in disguise:

- **No authorization state.** The thesis's lifecycle is Request → Triage → Design → Approval → Execution → Acceptance → Sustain and insists approval and acceptance are separate moments. Map it: `open` (request/triage), `planning` (design), **nothing** (approval), `active` (execution), `review` (acceptance), `done`, **nothing** (sustain). In a PR workflow nobody approves starting a ticket, so the gap is invisible; everywhere else (hospital, legal, hardware ECO, the thesis's own Phase 3) it is the main gate.
- **`done` = accepted = in effect.** True of a merge if you squint; false of a deploy, a go-live, a published policy, a shipped game build.
- **No retirement.** Intake bucket "retire" (decision 14) has no terminal state.
- **`blocked` is a flag, not a state.** Blocked-while-planning and blocked-while-active collapse to one value, and un-blocking loses where you were. DARKFOG has no `blocked`; Linear does. It is here because Linear has it.
- **Meanings are defined in delivery terms.** "Work complete, awaiting acceptance" presupposes the work precedes the acceptance.

The decision vocabulary (`proposed · decided · superseded · reverted`) is more neutral but lacks `rejected` (DARKFOG) and will lack `expired`/`defaulted` once bounded asks exist.

The honest framing is: *the default vocabulary is delivery-shaped and the thesis's "domain-agnostic core" claim is about record types, not states.* Either say that, or add the authorization and effective states now, before an organisation's mapping is written against the current set.

## Actor model failures

Rule under test: "an actor is a definition; a session is a run; a spawn is a session, never an actor."

1. **Long-lived autonomous agent with no human-named definition.** A nightly drift-sweeper daemon runs for months. It is `agent:drift-sweeper`; each night is a session. Its prompt is edited forty times. Every session has the same `agent`, and nothing on the session records which definition version ran (`links` on the actor points at *a* definition file, unversioned; `ext.model` is optional and unvalidated). Wrong accountability: a bad write in week 30 is attributed to the same actor as week 1, though the thing that acted is different code. The only human in the chain is `actors/drift-sweeper.md`'s `writer` (whoever first mentioned it), and the schema never states that `actor.writer` is the responsible party.
2. **Model changes mid-run.** Claude Code `/model` switches Sonnet to Opus halfway through a session. The session has one `ext.model`; the store's own `actors/claude-code.md` puts `ext.model: claude-fable-5-1` on the *actor*, which makes the harness actor a model identity. Records written after the switch carry a `session` whose `ext.model` is wrong for them. Wrong accountability: writes attributed to the wrong model, and no field on the envelope to say otherwise.
3. **Ad hoc subagent defined by a prompt.** This review is such a spawn: `general-purpose` with a custom prompt, no definition file. Its session's required `agent` can only be `agent:claude-code` (the harness). So an adversarial reviewer, a code generator and a release note writer spawned by the same harness are indistinguishable in the index; the thing that made them different (the prompt) is not retained. Worse, "created on first mention" means an adapter that writes `agent: agent:reviewer-6` on a session *mints an actor*. The rule "a spawn is never an actor" is a convention nothing checks; the index cannot tell a definition from a handle somebody typed.
4. **Two harnesses, one definition.** `agent:code-reviewer` runs under Claude Code (`.claude/agents/code-reviewer.md`) and under Cursor (a rules file with different content), with different models. Same handle, two behaviours, two sessions. Wrong accountability: a decision `decided_by: agent:code-reviewer` names a role, not an agent; there is no human behind it unless `actor.writer` is given that meaning, which the schema does not do.
6. **Agent-decided decisions with no scope policy.** Tenet: "day one, every scope requires a human." v2 validation checks only that `decided_by` resolves. An agent can set `status: decided, decided_by: agent:code-reviewer` on any decision and the store is valid. Phase 1's effective policy is the inverse of the stated one: no scope requires a human.
7. **A person's session.** The session field is `agent`, required. A human-run session (`agent: person:vinh`) is grammatical and reads wrong; decision 30 says the kinds are interchangeable, the field name says they are not. Either rename it or forbid person sessions explicitly.

## Provenance chain breaks

"Every write has provenance" rests on three legs: `writer`/`session` on the record, `parent`/`agent` on the session, and git (`blame` + a `Pjman-Session:` trailer). Where each breaks:

- **The store does not do it.** `git log --format='%(trailers:key=Pjman-Session)'` over the 26 commits in this repository returns zero trailers. The walk-through store violates the layer-0 requirement it introduces. (Commits carry `Co-Authored-By: Claude Fable 5.1`, which names a model, not a session or an actor record.)
- **Uncommitted writes.** A record written by an agent and never committed has provenance exactly equal to what the agent typed into `writer:`. There is no signature, no check that the session id exists at write time (validation is at index build), and no rule that `writer` must equal the session's `agent`.
- **Squash merges.** GitHub's squash takes the PR title/body, not per-commit trailers. N sessions' trailers collapse into zero. Rebases keep trailers but rewrite the committer; `git blame` then attributes to the rebaser.
- **GUI or editor saves.** Obsidian, VS Code, a web form: no trailer, no session, `updated` not bumped (it is D, so bumping it by hand is drift; not bumping it is a stale derived field). The validator detects "a hand edit to a derived field" only by comparing to "what the deriver last wrote," and the only place that baseline exists is git. In a non-repo store, derived-field drift is undetectable.
- **MCP server, on behalf of an agent, on behalf of a human.** The chain is human → harness session → MCP tool call → library write. The MCP server is not an actor. The session belongs to the harness. The human has no field (scenario 5). Three parties, one `writer`.
- **`writer` and `session` are marked D but are hand-typed on the only record a person is expected to write.** By the schema's own rule ("a derived field is never hand-written; its deriver is its only writer"), every hand-written decision in `.pjman/decisions/` is invalid. The A/D marking on the envelope is wrong or the decision record's authoring story is.
- **Hosted "audit log."** Named as a requirement, not specified; nothing says what it records, so the Phase 2 schema-over-database cannot be checked against it.

## Coordination through the record — true or aspirational

What v2 provides for agent-to-agent coordination:

- **Claim / lease.** Nothing. The nearest is `status: active` plus `owner` (defaults to writer). Both are authored fields any actor can set; two agents reading the same `open` change at once both set `active`, both become owner, and the files merge-conflict or last-writer-wins. No `claimed_by`, no `lease_until`, no compare-and-swap on `updated` in the library contract.
- **Ask.** Nothing addressable. A `proposed` decision is the only way to pose a question, and it has no addressee (`decided_by` is filled only after the fact), no `due`, no `default`, no notification. Those are explicitly deferred to layer 4 (the bounded ask).
- **Handoff.** Reassigning `owner`. No from, no reason, no acknowledgement, no record of the handoff as an event (sessions could observe it, but only if an adapter notices).
- **Conflict rule.** Stated only for observed edges ("append-only ... merge without arbitration"). Authored fields on `change.md` have no rule; with files in git the rule is git's.
- **Messages.** The thesis says "never through messages." The Agent tool returns a subagent's report to its parent as a message; DARKFOG files it verbatim precisely so it becomes a record. v2's session body is "free," so the report *may* land there; nothing requires it, and nothing can reference it once it does (sessions are not link targets).

Conclusion: in v2, "coordination through the record" is true for one thing (observed-edge logging) and aspirational for claiming, asking, handing off and resolving. The thesis presents it as a property of the substrate (decision 30, "Phase 1 consequence: one field"); it is a property of layer 4 plus a library concurrency contract that does not exist yet. Either restate the claim as Phase 2+ or put a minimal claim primitive in layer 2.

## Handle-reference failures

Actors are referenced as `person:<handle>` / `agent:<handle>`, "the one deliberate exception to id-only references."

1. **Two stores merge.** Phase 2 ("a team adopts its own subtree ... larger companies join by ingestion") merges stores into an organisation graph. Both have `person:alex`. Every other record type survives a merge because references are ids and folders are renameable; actor references do not, because the id on `actors/alex.md` is never used by anything. `aliases` cannot help: it resolves renames of one actor, not collisions between two. The one record type that *most* needs cross-store identity (people) is the one that lacks it.
2. **Handle reuse after departure.** `person:alex` leaves; a new Alex joins and takes `alex`. History (`decided_by: person:alex`) silently re-points to the new person. Ids would not.
3. **Model name as agent handle.** The store uses `agent:claude-code` and hides the model in `ext`; a user who names the actor after the model (`agent:claude-sonnet-4`) renames it at deprecation and relies on `aliases`. Two actors claiming the same alias (a renamed agent and a renamed person, or two renamed agents) make a reference ambiguous; the validation rule is "every referenced handle exists," not "resolves uniquely."
4. **The prefix duplicates `kind`.** `person:`/`agent:` encodes kind in every reference while `kind` lives on the actor. Correcting a mis-created actor's `kind` (a bot created as a person) invalidates every reference to it, which an id reference would not. Two sources of truth for one fact.
5. **No normalisation rule.** `Vinh` vs `vinh`, unicode handles, handles with dots — the slug rule is specified for source filenames, not for handles. Case-insensitive filesystems will treat `Vinh.md` and `vinh.md` as one file and the index as two actors.
6. **Export boundary.** Phase 2 says files become the export format. Handle refs are store-relative; an export from one store imported into another is only safe if handles are globally unique, which nothing guarantees.

## What must change before code

1. **Put the human back on the session.** A required `principal`/`user` (the pruned `on_behalf_of`) on every session whose `agent` has `kind: agent`. Without it, Phase 1 step 4 (the second user) produces unattributable records and "every write has provenance" is false on day one.
2. **Make sessions linkable.** Either let `links` on change/decision accept any record id (not only sources), or add a `sessions` edge. Rounds, verdict evidence, "which run noticed this" and DARKFOG's agent reports all depend on it; so does layer 4's `evidence`.
3. **Decide containment.** Restore `parent`/`parents` on change, or add a `relates: [{edge, to}]` list on change with `depends_on`, `split_from`, `supersedes`, `child_of` as data. "A milestone is a change" and "a Linear ticket is a change" are both false for a flat set; the Phase 2 sync will need this on its first import.
4. **Make provenance work without git, or stop allowing stores without git.** Either (a) the user-space store is a git repository by construction, and the location rule says so, or (b) the library keeps an append-only write log in the store (`log/` or a per-record history) that gives `writer`, `session`, timestamp and the derived-field baseline. (b) also fixes derived-field drift detection, which currently has no baseline outside git. And write the trailers: the store's own commits have none.
5. **Fix the envelope's A/D marks.** `writer` and `session` are authored when a person writes a decision by hand. Mark them "D when written by the library; A on a hand-written record, validated against the committing session where one exists."
6. **Allow a group as a decider.** `kind: group` with `members: [actor ref]`, or a `decided_by: [actor ref]` list. Committees, review boards and pairs decide things in every domain including this one.
7. **Add the authorization state and the effective state** (`approved` between `planning` and `active`; `done` split from `live`/`in-effect`, or a `retired` terminal) — or remove "domain-agnostic" from the vocabulary's claims and document it as delivery-shaped by default. Define `blocked` as a flag or drop it.
8. **Rename session `agent` to `actor`** or state that sessions are agent-only.
9. **Make "spawn is never an actor" checkable.** A session's `agent` must reference an actor that already exists (no create-on-first-mention from session writes), and an actor record must carry something a spawn cannot (a `definition` source link, validated present for `kind: agent`). Capture the definition version and model on the session as validated fields, not `ext`.
10. **Give humans a way to report observed state.** An authored `reported: {status, at, by}` on a source, or a sanctioned human-written observed edge, so "drift detection degrades to human report" is something the schema can hold rather than something it flags as drift.
11. **Reference actors by id like everything else**, rendering handles in views and accepting handles at the CLI; or, if handles stay, specify uniqueness, normalisation, and a store-qualified form (`vinh@pjman`) for merges and exports.
12. **Either add a minimal claim primitive to layer 2** (`claimed_by`, `claimed_at`, library-enforced check on `updated` at write) **or restate decision 30's "agents coordinate through the record" as a Phase 2+ property.** As written it is a promise the Phase 1 substrate cannot keep.
13. **Transition timestamps.** Either a `history: [{status, at, by}]` list on change (authored, append-only) or an explicit statement that status history is git's job, which then forbids non-git stores (see 4).
14. **Enforce "every scope requires a human" in Phase 1** with one rule: a decision may be `decided` by an agent only if `pjman.yaml` says so for that store. Otherwise the default policy is the opposite of the tenet.
