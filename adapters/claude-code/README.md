# pjman adapter for Claude Code

A plugin: seven hooks, one hooks module (`hooks/wake.ts`, below), four skills (`pjman`, the working rules; `intake`, how a request becomes a record; `map`, how a product gets its tree, or a better one; `aspect`, what applies across the product: its base shaped by its kind, forks kept to what differs, reconciled when the base changes) and one MCP server declaration (Linear's hosted server, so a session can read tickets after the person signs in with `/mcp`; the tool itself never signs in anywhere). Every write goes through `pjman`; the plugin holds no record logic of its own. The view beside the session is `pjman view`, rendered by the tool and docked by the plugin.

| Claude Code event | What happens |
|---|---|
| `SessionStart` (startup, resume, clear, compact, fork) | in a git repository that is not a project yet, runs `pjman init` so it becomes one (`auto_register: false` in `~/.pjman/config.yaml` turns that off). Outside any repository (a parent directory, the home folder), with a global store, the session is recorded there with no project and told so; the first tool call that lands in a registered repository (a file written there, a `cd` into it in a shell command) resolves it to that project (`pjman session project`), and every later hook call runs from that repository. Inside cmux the view is docked first, before any store call: the pane opens on the product's bridge, and follows the session once the start binds a change. Inside Rex, whose blocks are terminals only, the follow window is opened instead when none is open: once the session's record exists a detached copy of the hook starts the dashboard if none runs, tells it the session, asks it whether to open the window (yes to one caller only, so sessions started together never open two) and runs `pjman open --follow` (`follow_window: false` in `~/.pjman/config.yaml` turns that off; `follow_browser` names the browser). Then the reads run side by side (`pjman brief`, `pjman context`, `pjman whoami --verify`, the receipt's watermark, `pjman ls change --status done --json`, the open pull request off main), then the one write: `pjman session start <id> --log <line> [--branch <name>] [--full]` creates `session:<id>` unless it exists, appends the start line, binds the change the branch names when nothing is bound yet (its last segment the change slug, less the harness's `worktree-` prefix; a desktop worktree branch, `claude/<name>-<6 hex>`, less its suffix when the name as written finds no change) and observes the branch edge, and returns the brief: the bound change's context in full on resume, compact and clear, or when the binding moved. Worktrees whose change is done and whose branch is merged are named ahead of the board, with the command that removes each: the done changes' branch and worktree names (on the listing's rows) matched against one `git worktree list` and one `git branch --merged`, so the start costs the same however many worktrees there are. `PJMAN_HOOK_TIMING=1` logs each call's duration to `hook.log` |
| `UserPromptSubmit` | the prompt goes to `pjman refs`, which returns every reference in it (`change:<slug>`, an existing hyphenated slug, a ticket in any shape the store's source kinds know, a URL) with the change each leads to; the last one binds the session (a bare `#12` is weak and never binds: write `owner/repo#12` or the issue's URL; a pasted image's `[Image #2]` is not a reference), and the branch and open pull request are observed as its sources. The hook holds no pattern of its own. A ticket of the project's `tracker` with no record is read from the tracker and created through the sync (GitHub: the hook runs `gh issue view` and `pjman sync github` itself; otherwise the agent is told to read it and sync); a pattern match alone never creates a record. A prompt naming several changes binds none and the agent is told the candidates. Then the brief: in full when the binding moved, else what changed since the last brief; nothing when nothing did. Last, a running dashboard is told the person is on this session (`POST /follow`), and the follow window, wherever one is open, goes there |
| `PostToolUse` (Write, Edit, MultiEdit, NotebookEdit, Bash) | an edit, or a shell call that writes the store (`pjman new|set|note|session|mv|rm|order|apply|undo|fmt|init`), marks the turn as having acted; a file write in the project records an observed `links` edge from the bound change to `file:<path>`, the path read against the checkout the file sits in when that is a worktree of the project (the desktop app runs a worktree session's hooks from the main checkout) and marks the turn as having written code. A shell call that may bind (`pjman new|session|apply`: filing a change binds the session to it) reads the session's binding, and a change bound there that the hook has not taken up yet is taken up as a prompt's bind is: the sidebar names it and a parked pane follows to the session's page. A shell call that only reads, builds or tests does not count; a file edited through the shell is not observed |
| `Stop` | first, run to the end: when the turn wrote code for the bound change, the stop is allowed only where the change rests, which `pjman rest <change>` decides from the record (a decision proposed on it, a blocker recorded, a status a person set, the plan run to its end); anywhere else the stop is refused once, with the open steps and the three ways out (a decision opened, a blocker recorded, the plan finished and committed for review), and the turn goes on. The harness marks the retry (`stop_hook_active`), which passes, so a refusal is one push back into the plan, never a loop; a turn that only talked, and a subagent, pass untouched. Next, questions become decisions: a reply on a bound change that asks the person to choose (a question with alternatives in it, one followed by a list of options, one under an "open questions" line, or several questions together; or the harness's own question prompt used this turn) while no decision was opened or added this turn is sent back once, with the questions named and the way to record each as a proposed decision (`pjman decision <change>/<slug> …`). Then the size of every brief given this turn (`pjman briefed:`, lines and approximate tokens, and whether the harness cut it at 10,000 characters); if the turn acted, appends one log line from the first line of the assistant's message; then shows the person the receipt, `pjman events --receipt` since the last turn: what the store received, one line per record, composed by the tool so it reads the same every time |
| `SubagentStart` / `SubagentStop` | a child session with `parent`, and its own log line |
| `SessionEnd` | a closing log line; the view's pane is closed, or parked on the product's bridge when the session was cleared, from whatever page the person had browsed it to (a pane already on the bridge keeps its pins and position); the block's label on the host is cleared |
| module `wake.ts`: session start, then for the session's life | starts one follower, `pjman wakes --session <id> --follow`, which prints a line for each event that asks this session to act: a decision on its bound change set decided, a note on that change or on the session itself (`pjman note`), by anyone but the session. On a line the module submits one line naming it as a turn of its own, which Claude Code runs once the session is idle and never inside a running turn; the `UserPromptSubmit` hook then briefs as on any prompt, which carries the decision or the note in full and moves the watermark. Every other write waits for the next prompt. A follower that exits is started again after a pause that doubles to five minutes, and not after five quick exits in a row; it exits by itself once Claude Code is gone. Interactive sessions only: a terminal session from its start, a desktop app session (hosted through the SDK, so not interactive at start) once its window attaches. Because this module wakes the session, an acceptance is never also typed into it through its host; a harness without such a module is told through the host instead (`../hosts.md`, Delivery) |

**The view beside the session.** Inside cmux, at session start the plugin finds the dashboard server (`~/.pjman/serve.json`) or starts `pjman serve`, and docks a browser pane on the product's bridge, `/bridge/<product>`: every live session, what waits on the person, the product's motion, the view that reads on its own while the session has no subject. Once the session binds a change, from its branch at start, from a prompt, or by the agent filing or binding one, the pane is pointed at the session's page, `/session/<id>`; a session that never binds leaves it on the bridge. At that width the session page is the dock, one column: what the session is on, the decisions waiting on the person, the handoff, the session's own log lines, the summary, then rows into the record. It follows the session as it binds, live over the event stream. The tab remembers its session, so the pill in the top bar brings the person back from anywhere in the app, and names the change, never the id. The pane belongs to the terminal, not the session: it closes when the session ends, except on `/clear`, where it is sent back to the bridge from whatever page the person had browsed it to (one already on the bridge keeps its pins and position) and parked there, and the next session in that terminal takes it over the same way, once it binds a change; a parked pane closes with the session that ends without binding (a second terminal keeps its own pane). A session the pane already shows (resumed, compacted) leaves it where it is. The session's id is exported to the agent's shell as `PJMAN_SESSION`, so `pjman open` brings the page back after the pane is closed, and opens it in the default browser in any other terminal. Inside a host the tool knows (a terminal multiplexer: Rex, cmux), the session's block carries the bound change and where the work stands, written by `pjman host label` at a bind, after a turn that wrote the store, and cleared at the end; the session's record says which host it runs in, and the dashboard reads the session's state from the host where the host reports it. The hosts and what each gives are in [`../hosts.md`](../hosts.md).

Binding follows what the session does, never the agent's judgment: a change the prompt names (one; several bind none), a change the session creates (the tool binds it), a branch cut for a change; a write marks a change touched in the receipt and does not bind. Focus, the change the dock follows, moves with what the session reads (`pjman context <change>` run in the session) and writes. The brief (`pjman brief --session <id>`) is the tool's: the bound change's context in full when the binding moved, otherwise what others changed on it, its milestone, its decisions and its dependency edges since the last brief, one line per record, and the other live sessions on the same change or feature node; it records its watermark on the session, has no ceiling, and its size is shown to the person beside the receipt. The log line is the harness's own text; no model is called. The hook never blocks and never fails a session: errors go to `~/.pjman/claude-code/hook.log`. The adapter keeps its files there (the log, each session's state, the docks) rather than in the plugin's data folder, which removing or repointing the marketplace deletes; what an earlier version left in that folder is carried across once.

## Install

`pjman init` installs this plugin when `claude` is on PATH; the rest of this section is the manual route.

For a session:

```bash
claude --plugin-dir /path/to/pjman/adapters/claude-code
```

Permanently, add this repository as a marketplace and install from it, from GitHub or from a checkout:

```
/plugin marketplace add vinhvanvu/pjman
/plugin install pjman@pjman
```

```
/plugin marketplace add /path/to/pjman
/plugin install pjman@pjman
```

The plugin and the tool are one package: `pjman init` points the marketplace at the installed copy of pjman, so the hooks and the skills come from the same build as the command they call. A marketplace added from GitHub follows the repository's main branch instead.

The user config `~/.pjman/config.yaml` names the person the sessions run for (`actor: person:<handle>`); `pjman init` sets it, from the forge login, else the committer name, else the machine's account name. At session start (startup and `/clear`, never on resume, compact or in a subagent) the hook runs `pjman whoami --verify` and injects one block only when something is off: a provisional handle (no account of a handle kind claimed), a sign-in another person claims, an account the app does not know. The block carries the command that resolves it; the agent offers it to the person and never runs a rename or a claim unasked. The tool caches the apps' answers for a day, so the check costs a session start nothing after the first.

## What the skills add

`skills/pjman/SKILL.md` carries the rules an agent follows in a pjman project: read the change's context first, open a decision `proposed` before a choice that forecloses options and never accept it, run the plan to its end once the go is given and stop only where the change rests, leave the plan where the work stands before stopping, name new work as `change:<slug>`. `skills/intake/SKILL.md` is how one request becomes a record: duplicates first, then four questions with defaults. `skills/map/SKILL.md` is how a whole product gets its map: when `pjman context` says the product has none (or the person asks for a regrouping), survey the person's words, the documentation, the code's split and the store, draft the top level as the layers of the stack titled as sentences, propose the whole tree in a proposed decision, apply it on the go as one batch (`pjman apply`, which `pjman undo` reverts), verify. Skills load on demand, so for a rule that must hold every session add one line to the project's `CLAUDE.md`:

```markdown
This project has a pjman store. Follow the `pjman` skill: read `pjman context change:<slug>` before working on a change, open decisions `proposed` before acting, and leave the plan where the work stands before stopping.
```
