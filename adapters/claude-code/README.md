# pjman adapter for Claude Code

A plugin: seven hooks, one hooks module (`hooks/wake.ts`, below), four skills (`pjman`, the working rules; `intake`, how a request becomes a record; `map`, how a product gets its tree, or a better one; `aspect`, what applies across the product: its base shaped by its kind, forks kept to what differs, reconciled when the base changes) and one MCP server declaration (Linear's hosted server, so a session can read tickets after the person signs in with `/mcp`; the tool itself never signs in anywhere). Every write goes through `pjman`; the plugin holds no record logic of its own. The view beside the session is `pjman view`, rendered by the tool and docked by the plugin.

| Claude Code event | What happens |
|---|---|
| `SessionStart` (startup, resume, clear, compact, fork) | in a git repository that is not a project yet, runs `pjman init` so it becomes one (`auto_register: false` in `~/.pjman/config.yaml` turns that off). Inside cmux the view is docked first, before any store call. Then the reads run side by side (`pjman brief`, `pjman context`, `pjman whoami --verify`, the receipt's watermark, `pjman ls change --status done --json`, the open pull request off main), then the one write: `pjman session start <id> --log <line> [--branch <name>] [--full]` creates `session:<id>` unless it exists, appends the start line, binds the change the branch names when nothing is bound yet (its last segment the change slug, less the harness's `worktree-` prefix) and observes the branch edge, and returns the brief: the bound change's context in full on resume, compact and clear, or when the binding moved. Worktrees whose change is done and whose branch is merged are named ahead of the board, with the command that removes each: the done changes' branch and worktree names (on the listing's rows) matched against one `git worktree list` and one `git branch --merged`, so the start costs the same however many worktrees there are. `PJMAN_HOOK_TIMING=1` logs each call's duration to `hook.log` |
| `UserPromptSubmit` | the prompt goes to `pjman refs`, which returns every reference in it (`change:<slug>`, an existing hyphenated slug, a ticket in any shape the store's source kinds know, a URL) with the change each leads to; the last one binds the session (a bare `#12` is weak and never binds: write `owner/repo#12` or the issue's URL; a pasted image's `[Image #2]` is not a reference), and the branch and open pull request are observed as its sources. The hook holds no pattern of its own. A ticket of the project's `tracker` with no record is read from the tracker and created through the sync (GitHub: the hook runs `gh issue view` and `pjman sync github` itself; otherwise the agent is told to read it and sync); a pattern match alone never creates a record. A prompt naming several changes binds none and the agent is told the candidates. Then the brief: in full when the binding moved, else what changed since the last brief; nothing when nothing did |
| `PostToolUse` (Write, Edit, MultiEdit, NotebookEdit, Bash) | an edit, or a shell call that writes the store (`pjman new|set|note|session|mv|rm|order|apply|undo|fmt|init`), marks the turn as having acted; a file write in the project records an observed `links` edge from the bound change to `file:<path>`. A shell call that only reads, builds or tests does not count; a file edited through the shell is not observed |
| `Stop` | the size of every brief given this turn (`pjman briefed:`, lines and approximate tokens, and whether the harness cut it at 10,000 characters); if the turn acted, appends one log line from the first line of the assistant's message; then shows the person the receipt, `pjman events --receipt` since the last turn: what the store received, one line per record, composed by the tool so it reads the same every time |
| `SubagentStart` / `SubagentStop` | a child session with `parent`, and its own log line |
| `SessionEnd` | a closing log line; the view's pane is closed |
| module `wake.ts`: session start, then for the session's life | starts one follower, `pjman wakes --session <id> --follow`, which prints a line for each event that asks this session to act: a decision on its bound change set decided, a note on that change or on the session itself (`pjman note`), by anyone but the session. On a line the module submits one line naming it as a turn of its own, which Claude Code runs once the session is idle and never inside a running turn; the `UserPromptSubmit` hook then briefs as on any prompt, which carries the decision or the note in full and moves the watermark. Every other write waits for the next prompt. A follower that exits is started again after a pause that doubles to five minutes, and not after five quick exits in a row; it exits by itself once Claude Code is gone. Interactive sessions only. |

**The view beside the session.** Inside cmux, at session start the plugin finds the dashboard server (`~/.pjman/serve.json`) or starts `pjman serve`, and docks a browser pane at the session's page, `/session/<id>`. At that width the page is the dock, one column: what the session is on, the decisions waiting on the person, the handoff, the session's own log lines, the summary, then rows into the record; before a bind, the product's board. It follows the session as it binds, live over the event stream. The tab remembers its session, so the pill in the top bar brings the person back from anywhere in the app, and names the change, never the id. The pane is closed when the session ends. The session's id is exported to the agent's shell as `PJMAN_SESSION`, so `pjman open` brings the page back after the pane is closed, and opens it in the default browser in any other terminal. Inside cmux the bound change is named in the workspace sidebar.

Binding follows what the session does, never the agent's judgment: a change the prompt names (one; several bind none), a change the session creates (the tool binds it), a branch cut for a change; a write marks a change touched in the receipt and does not bind. Focus, the change the dock follows, moves with what the session reads (`pjman context <change>` run in the session) and writes. The brief (`pjman brief --session <id>`) is the tool's: the bound change's context in full when the binding moved, otherwise what others changed on it, its milestone, its decisions and its dependency edges since the last brief, one line per record, and the other live sessions on the same change or feature node; it records its watermark on the session, has no ceiling, and its size is shown to the person beside the receipt. The log line is the harness's own text; no model is called. The hook never blocks and never fails a session: errors go to `hook.log` in the plugin's data directory.

## Install

`pjman init` installs this plugin when `claude` is on PATH; the rest of this section is the manual route.

For a session:

```bash
claude --plugin-dir /path/to/pjman/adapters/claude-code
```

Permanently, add this repository as a local marketplace and install from it:

```
/plugin marketplace add /path/to/pjman
/plugin install pjman@pjman
```

The user config `~/.pjman/config.yaml` names the person the sessions run for (`actor: person:<handle>`); `pjman init` sets it, from the forge login, else the committer name, else the machine's account name. At session start (startup and `/clear`, never on resume, compact or in a subagent) the hook runs `pjman whoami --verify` and injects one block only when something is off: a provisional handle (no account of a handle kind claimed), a sign-in another person claims, an account the app does not know. The block carries the command that resolves it; the agent offers it to the person and never runs a rename or a claim unasked. The tool caches the apps' answers for a day, so the check costs a session start nothing after the first.

## What the skills add

`skills/pjman/SKILL.md` carries the rules an agent follows in a pjman project: read the change's context first, open a decision `proposed` before a choice that forecloses options and never accept it, leave the plan where the work stands before stopping, name new work as `change:<slug>`. `skills/intake/SKILL.md` is how one request becomes a record: duplicates first, then four questions with defaults. `skills/map/SKILL.md` is how a whole product gets its map: when `pjman context` says the product has none (or the person asks for a regrouping), survey the person's words, the documentation, the code's split and the store, draft the top level as the layers of the stack titled as sentences, propose the whole tree in a proposed decision, apply it on the go as one batch (`pjman apply`, which `pjman undo` reverts), verify. Skills load on demand, so for a rule that must hold every session add one line to the project's `CLAUDE.md`:

```markdown
This project has a pjman store. Follow the `pjman` skill: read `pjman context change:<slug>` before working on a change, open decisions `proposed` before acting, and leave the plan where the work stands before stopping.
```
